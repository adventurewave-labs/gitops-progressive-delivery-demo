0130-second cinematic demo

Watch the agentic loop fire end-to-end: Argo CD syncs → Argo Rollouts shifts canary traffic → Prometheus SLO burns → K8sGPT analyzes → GLM-4.5 diagnoses → auto-rollback.

Full pipeline walkthrough (26s)
RECORDED FROM LIVE APP
The full pipeline auto-loops every 40s. Every value on screen — traffic split, SLO badge, pod phase, analyzer findings, LLM diagnosis — comes from a real HTTP call to a real backend endpoint. No client-side state machine hiding the work.
K8sGPT terminal + real GLM-4.5 stream (14s)
REAL LLM CALL
The terminal runs k8sgpt analyze --explain --output json, fetches real analyzer findings, then makes a real GLM-4.5 call via the z-ai-web-dev-sdk. The LLM's structured response — Root Cause, Evidence, Impact, Recommended Action, Diagnosis — streams into the terminal line by line, just like token streaming from a real LLM API.
Rollout abort + traffic revert (10s)
ARGO ROLLOUTS
After the LLM diagnosis completes, the pipeline triggers an automated rollback. Argo Rollouts shifts 100% of traffic back to the stable ReplicaSet, the canary ReplicaSet scales to 0, and Prometheus metrics return to baseline within ~3 seconds.

03Real GLM-4.5 root-cause analysis

Captured verbatim from POST /api/explain. Real LLM call via z-ai-web-dev-sdk against Z.AI's GLM-4.5 model. Rendered below in the Slack incident-card format that K8sGPT would actually post.

#sre-incidents Robusta → K8sGPT → GLM-4.5 2026-08-20 22:17 UTC · model=glm-4.5 · cached=false

🔥 Root Cause

The payments-api-canary v2.4 pods are being terminated due to memory exhaustion, causing the canary deployment to fail SLO checks.

Evidence

  • Pod payments-api-canary-6b8f4c-9a8bc was OOMKilled (exit code 137)
  • Container 'api' logs show heap growth from 245MB to 1.0GB before termination
  • Deployment payments-api-canary has 2 replicas but 0 are available

Impact

The canary deployment is paused with 50% traffic, preventing the rollout of v2.4 and potentially causing service degradation if the stable version is also affected.

Recommended Action

  1. kubectl logs payments-api-canary-6b8f4c-9a8bc -c api --previous
  2. kubectl logs payments-api-canary-6b8f4c-9a8bc -c api --previous | grep -i memory
  3. kubectl argo rollouts promote payments-api -n payment-prod

Diagnosis

The v2.4 canary pods are failing due to memory leaks causing heap growth beyond allocated limits, resulting in OOMKilled termination (exit code 137). The canary traffic split is exposing these memory issues under production load, while v2.3 remains healthy with proper memory management.

05The stack

Five components, every one replaceable. Swap the mock kube-apiserver for a real one and everything else keeps working.

A

Argo CD

GitOps sync engine

Syncs the new Git commit main@a1b2c3d into the payment-prod namespace. The sync arrow pulses amber during the 3s apply window, then flips to emerald when manifests are committed to the cluster.

API: /api/cluster-state → argoCdSync
R

Argo Rollouts

Canary + traffic shifting

Drives the canary: 20% → 50% traffic shift, pauses on the analysis step, aborts on failure. The traffic pipe animates in real-time as Argo Rollouts shifts weight between stable and canary ReplicaSets.

API: /api/cluster-state → argoRollouts
P

Prometheus

SLO metrics

Scrapes http_error_rate and http_request_duration_p99 for the canary pods. When the canary breaks, error rate spikes to 15.2% and p99 latency to 2042ms — both clearly visible in the live recharts.

API: /api/prometheus?query=...
K

K8sGPT

SRE agent (rule-based)

Runs 8 structured analyzers mirroring k8sgpt's Go code (Pod, Deployment, Rollout, PVC, Node, log). Returns 9 real findings in k8sgpt's JSON shape — no LLM at this stage, just deterministic rule-based detection.

API: /api/analyze · 9 problems in 126ms
G

GLM-4.5 (Z.AI)

LLM brain — REAL API calls

For each finding, the LLM produces a structured root-cause analysis citing specific pod names + kubectl commands. Called via the z-ai-web-dev-sdk. Server-side cached so demo re-runs are instant.

API: /api/explain · model=glm-4.5
